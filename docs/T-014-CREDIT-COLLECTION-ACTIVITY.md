# T-014 — Credit Collection Activity v1

Official identity: **T-014 CREDIT_COLLECTION_ACTIVITY**. It records that a collection management (call, visit, ...) happened on
a loan, as append-only business history. It is metadata: it moves no money, changes no debt, loan status, assignment or
worklist, and stores no content of the interaction.

## Model

Table `credit_collection_activities`, exactly: `id, tenant_id, loan_id, managing_branch_id, recorded_by, assignment_id,
activity_type, created_at, idempotency_key, request_digest`.

* **Target = the loan** (`credit_loans.id`). Two loans of one customer have independent activities. Customer-only, obligation,
  route, portfolio or assignment-as-target activities do not exist (DEFER / BLOCKED_BY_SPEC).
* **Actor = the authenticated user** (`recorded_by`); the performer is the same person, so there is no duplicate `performed_by`
  column. No proxy (a supervisor recording "as" another collector) in v1.
* **`activity_type`** is a closed enum (also a DB CHECK): `phone_call`, `whatsapp`, `sms`, `email`, `in_person_visit`,
  `office_visit`, `no_contact`, `other`. `promise_created`, `promise_broken`, `payment_received` and `note` are NOT types
  (promise → T-015, payments → the T-008/T-009 ledger, `note` without text has no meaning). `whatsapp`/`sms`/`email` only record
  that such a management happened: nothing is sent and no provider is called.
* **No outcome** (catalogue deferred), **no free text** (`observation`, `note`, `notes`, `comment`, `description`,
  `free_text`), **no contact data** (phone, e-mail, address, document, destination), **no GPS**, **no attachment**. Any such
  field is a 422 (the schemas forbid unknown fields), so there is no PII surface and no retention/redaction policy to invent.
* **Time**: `created_at` is generated by the server. No `occurred_at`, activity/business date, scheduled or future timestamp,
  no backdating.
* **Snapshots (server side, never from the client)**: `managing_branch_id` = the loan's managing branch at INSERT (may be NULL;
  immutable) and `assignment_id` = the OPEN T-012 assignment of the loan at that instant, or NULL. They are history, not
  authority: authorization is always recomputed against the loan and the current RBAC. After a reassignment or an end the
  activity keeps the snapshot it took.

## Authorization

* **Write** `POST …/collection-activities`: the new sensitive tenant permission **`collections.actions.create`** (seeded to the
  tenant admin roles by migration 0016; not to the legacy `collector` role) on the loan's **managing branch**; a loan without one
  needs a **tenant-level** grant. No `collections.read` is required to write. Origin, disbursement or receiving branch,
  `collections.assign`, `loans.read`, the user's branch and the legacy role string never substitute it.
* **Read** `GET` list/detail: `collections.read` on the same boundary (tenant-level for a loan without managing branch). Being
  the recorder, or the snapshot assignee, grants nothing.
* **The assignment neither authorizes nor restricts**: the actor need not be the assignee, and a loan being assigned opens no door
  (tested: a read-only user and the assignee itself get 403).

## Commands and idempotency

`POST /api/v2/loans/{loan_id}/collection-activities` with exactly `{activity_type, idempotency_key}` → 200 with `activity_id,
loan_id, managing_branch_id, recorded_by, assignment_id, activity_type, created_at, replayed`. Never the key or digest.

One transaction, lock order **loan `FOR UPDATE` → the open assignment row (read) → INSERT**. The loan lock serializes it with
T-012 assign / reassign / end, so the snapshot is the assignment that was current in that serial order (either order is valid).
It takes no obligation, payment, reversal or Cash lock and does not read the balance.

* `(tenant_id, idempotency_key)` UNIQUE + `request_digest` of `(operation=create_collection_activity, loan_id, activity_type)`
  (never time, actor, tenant, branch or assignment). Same key and digest → 200 replay of the existing row (0 INSERT, 0 audit).
  Same key with another type or another loan → 409 `idempotency_conflict`.
* **Authorization runs before the replay** (loan resolved, tenant and permission re-checked): a key is never an access bypass; a
  user that lost the permission gets 403 on its own replay.
* Concurrent identical requests: the loan lock makes one create and the other replay; the UNIQUE constraint is the backstop. No 500.

## Lifecycle

Any stored loan status accepts an activity (active, past_due, paid, restructured, ...): it is history, not a financial
transition. No overdue requirement, no use of `loan.status` as a gate, and the status is never written.

## Reads

`GET …/collection-activities` newest first (`id DESC`), keyset (`id < cursor`), default 50, max 100, no public OFFSET (an `offset`
parameter is ignored). The cursor is a strict opaque `{"i": <positive int>}`; anything else is 422 `invalid_cursor`; it never
carries scope (RBAC is recomputed). Live read: no snapshot across requests. `GET …/collection-activities/{id}`: another loan's,
another tenant's or a missing id is the same safe 404. Responses: `activity_id, loan_id, managing_branch_id, recorded_by,
assignment_id, activity_type, created_at` only. GETs do 0 INSERT/UPDATE/DELETE and 0 audit.

## What the database enforces (migration 0016)

| Invariant | Mechanism |
|---|---|
| append-only | BEFORE UPDATE/DELETE trigger: always refused (no correction, void or supersede in v1) |
| the type is an approved one | CHECK `activity_type_valid` |
| idempotency | UNIQUE `(tenant_id, idempotency_key)` |
| tenant-safe references | composite FKs: loan `(tenant_id, loan_id)`, actor `(tenant_id, recorded_by) → users(company_id, id)`, branch, and assignment `(tenant_id, assignment_id, loan_id)` |
| the snapshots are the loan's | BEFORE INSERT trigger: `managing_branch_id` = the loan's, `assignment_id` = the open assignment of the loan or NULL |
| list performance | index `(tenant_id, loan_id, id)` (the only extra one) |

To make the assignment FK tenant-safe AND same-loan, migration 0016 adds to `credit_collection_assignments` only the UNIQUE
`(tenant_id, id, loan_id)` (`uq_credit_collection_assignments_tenant_id_loan`): relational support, no change to any T-012 rule.
(`users` needed nothing: `uq_users_tenant_id` came with T-012.)

**Downgrade 0016 → 0015** refuses to run, before any DDL, when the table has rows (it would erase collection history); with an
empty table it is clean (drops the table, the support UNIQUE, the permission and the functions) and re-upgrade works.

## Audit

`loan.collection_activity_created` with `activity_id, loan_id, loan_number, activity_type, recorded_by, assignment_id,
managing_branch_id` (+ the usual request context). No PII, text, contact destination, key or digest. The table is the business
history; the audit is the command record. No audit on replay, on a failed command or on reads.

## Not in T-014

No promise-to-pay, follow-up/agenda/scheduler, outcome catalogue, free-text observation, GPS, attachment, messaging, worklist
field (`last_activity_*`) or filter, priority/score, Cash/custody/rendition, accounting/outbox, legacy import or dual-write
(`customers.notes`, `payments.notes`, `assigned_collector_id`, routes and `location_ping` are neither read nor written).
Retention, purge, redaction or regulatory handling is not implemented and no compliance is claimed (BLOCKED_BY_EVIDENCE).

**BLOCKED_BY_SPEC**: customer-only activity, proxy performer, structured outcomes, free-text notes and their PII/visibility policy,
backdated `occurred_at`, correction/void/supersede, promise-to-pay (fulfilment, partial payments, reversal, cancellation,
reassignment effect), follow-up/agenda, worklist enrichment, priority/score, field-payment coupling, retention and regulatory
policy, third-party contact, earlier pending items. **BLOCKED_BY_EVIDENCE**: scheduler/worker, messaging providers, attachment
storage, GPS policy, modern routes, team/provider/supervisor models, accounting, outbox.

## Known limitations

* A wrong activity cannot be corrected or removed in v1 (append-only by design; a correction semantic needs a spec).
* The `activity_type` enum is closed; a new type needs a migration.
* The snapshot assignee may have become ineligible (T-012 does not repair stale assignments); the snapshot says "it was the open
  assignment", not "it was valid".
* Reads are live: no snapshot between pages.
* Direction for T-015: PROMISE_TO_PAY discovery (target, amount/date, states, fulfilment, partial payments, reversal,
  reassignment) or read-only `last_activity_*` fields in the worklist.
